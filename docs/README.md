# Documenting an Amazon service extension

This guide is for developers and LLM agents who need to document a new extension, or change the documentation of an existing one.

Every service page is generated from a single skeleton, [`_fragments/amazon-guide-generic.adoc`](modules/ROOT/pages/_fragments/amazon-guide-generic.adoc). You never write a service page by hand. You provide:

- attributes, which fill in and switch on parts of the skeleton;
- optional files, which inject or replace content at fixed points.

A service page is always exactly these two lines:

```asciidoc
include::./_metadata/amazon-<page>.adoc[]

include::./_fragments/amazon-guide-generic.adoc[]
```

## Layout

```
docs/
├── templates/includes/attributes.adoc       global attributes (versions, quickstart URLs), filtered by Maven
└── modules/ROOT/
    ├── nav.adoc                             navigation menu, one entry per page
    └── pages/
        ├── amazon-<page>.adoc               the page itself: the two includes above
        ├── _metadata/amazon-<page>.adoc     generated by the build from the service model, do not edit (see below)
        ├── _description/amazon-<page>.adoc  intro text + editorial attributes (see below)
        ├── _extras/amazon-<page>-<point>.adoc            optional injected content (see below)
        ├── _fragments/amazon-guide-generic.adoc           the skeleton shared by every page
        └── includes/                        generated by the build, do not edit
            ├── attributes.adoc              copied from docs/templates/includes/attributes.adoc
            └── quarkus-amazon-<extension-name>.adoc        configuration reference of the extension
```

Antora does not publish folders whose name starts with `_`. Those files are only reachable through includes.

`<page>` is the page file name without the `amazon-` prefix (for example `cognitouserpools`). `<extension-name>` is the artifact name without `quarkus-amazon-` (for example `cognito-user-pools`). They are the same for almost every service. All the files of a service are named after its page: `amazon-<page>.adoc` in `_metadata/` and `_description/`, `amazon-<page>-<point>.adoc` in `_extras/`. The page name fixes the published URL and the `guide:` links, so it never changes.

## What a page renders

The skeleton always produces the sections below, in this order. Some only appear when an attribute is set, and some can be extended or replaced by an injection point.

| Section | Shown when | Injection point |
|---|---|---|
| Title `{service-name-uppercase} Client` | always | — |
| Intro (your text from `_description`) | always | — |
| « For more information, see the … documentation » | `aws-docs-url` | — |
| NOTE on the AWS SDK programming models | always | — |
| Prerequisites (« No AWS account is required », or a NOTE that the local stacks may not emulate the service) | always, depending on `has-integration-test` | — |
| Prerequisites → Start … automatically with Dev Services (with the `devservices.provider` property when `aws-stack` is not `floci`) | always | — |
| Prerequisites → Start … manually (`docker run`, local CLI) | always | — |
| Solution (with `quickstart`) or What you will build (without) | `solution-summary` | — |
| Walkthrough (with `solution-summary`) or Getting started (without) → Creating the Maven project | always | — |
| Walkthrough → Using the … client (injection of the sync client) | always, unless replaced | `usage` (replaces) |
| Walkthrough → Configuring … clients (HTTP clients; « Use Dev Services »; « Use a manually started … » with the local endpoint; « Use your AWS account » with the credentials and the Dev Services warning) | always | `configuration` (appended) |
| Walkthrough → Run the application in Dev Mode (what Dev Services provides; without `usage`, a hint to add endpoints) | always | `run` (appended) |
| Next steps → Packaging | always | — |
| Next steps → Going asynchronous (injection of the async client, then running it) | always, unless replaced | `async-usage` (replaces), `run` (appended again, with `run-async` set) |
| Next steps → Going further (recap, depending on `solution-summary`; links to the shared guides, the quickstart and `aws-docs-url`) | always | — |
| *(additional top-level sections)* | — | `extras` |
| Configuration Reference | always (plus `extra-config-reference`) | — |

## Adding a new extension

1. **Page**: create `pages/amazon-<page>.adoc` with the two includes shown at the top of this document.
2. **Metadata**: build the runtime module of the extension. The code generator writes `pages/_metadata/amazon-<page>.adoc`, which is committed. If a generated value does not fit, override it in `quarkus-customization.config` (see [`_metadata` attributes](#_metadata-attributes)).
3. **Description**: create `pages/_description/amazon-<page>.adoc` with the intro and, if needed, editorial attributes (see [`_description` attributes](#_description-attributes)).
4. **Extras** (optional): add files in `pages/_extras/` only for content that the skeleton cannot produce (see [Injection points](#injection-points)).
5. **Navigation**: add `* xref:amazon-<page>.adoc[<Service name>]` to [`nav.adoc`](modules/ROOT/nav.adoc), in alphabetical order.
6. **Extension metadata**: the code generator also writes the extension descriptor `META-INF/quarkus-extension.yaml` in `target/generated-resources/sdk-resources` of the runtime module (not committed). Its `name` is the display name, its `guide` points to `amazon-<page>.html` and its `config` prefix is `quarkus.<service-name>.`. Its keywords are the extension name, `aws` and `amazon`, and its category is `cloud`; add keywords or replace the categories in `quarkus-customization.config`:
   ```json
   {
       "keywords": ["email"],
       "categories": ["messaging"]
   }
   ```
   Its `status` is `stable`; set `"status": "deprecated"` in `quarkus-customization.config` for a service that AWS no longer supports. The documentation page then shows a deprecation WARNING (see `extension-status`); explain in the description why, and what to use instead.
7. **Configuration reference**: build the project (`./mvnw install -DskipTests`). This generates `pages/includes/quarkus-amazon-<extension-name>.adoc`, which is committed with the page.
8. **Check** the rendering (see [Checking the result](#checking-the-result)).

### Minimal example: API Gateway v2

`pages/amazon-apigatewayv2.adoc`:

```asciidoc
include::./_metadata/amazon-apigatewayv2.adoc[]

include::./_fragments/amazon-guide-generic.adoc[]
```

`pages/_metadata/amazon-apigatewayv2.adoc`:

```asciidoc
// Generated by quarkus-amazon-codegen-maven-plugin, do not edit.
:service-name: apigatewayv2
:service-name-uppercase: Amazon API Gateway V2
:service-class-name: ApiGatewayV2
```

It is generated. The display name comes from `services/apigatewayv2/src/main/resources/codegen-resources/quarkus-customization.config`, because the AWS model only provides `AmazonApiGatewayV2`:

```json
{
    "displayName": "Amazon API Gateway V2"
}
```

`pages/_description/amazon-apigatewayv2.adoc`:

```asciidoc
:aws-docs-url: https://docs.aws.amazon.com/apigatewayv2/latest/api-reference/api-reference.html

Amazon API Gateway is a fully managed service for creating, publishing and securing APIs at any scale.
This client uses the API Gateway V2 API to create, deploy and manage HTTP APIs and WebSocket APIs, with their routes, integrations, stages, authorizers and domain names.
To manage REST APIs, use the Amazon API Gateway extension.
```

This is enough for a complete page: prerequisites, Maven project, injection of `ApiGatewayV2Client` and `ApiGatewayV2AsyncClient`, client configuration and configuration reference.
As the integration tests do not cover API Gateway V2, the page warns that the local stacks may not emulate it.

## `_metadata` attributes

`_metadata/` is **generated** by `quarkus-amazon-codegen-maven-plugin` when the runtime module of a service is built, and committed like `includes/`. Do not edit these files: change the source of the value instead.

Every value is taken as is, without transformation, from the AWS service model, the Quarkus customization of the service (`services/<service>/src/main/resources/codegen-resources/quarkus-customization.config`) or the layout of the service folder. When a value does not fit, override it in `quarkus-customization.config`.

**Anything that is a writing choice, or that depends on the integration tests, belongs in `_description/`**, never in `_metadata/`.

| Attribute | Meaning | Source | Override in `quarkus-customization.config` | Example |
|---|---|---|---|---|
| `service-name` | Configuration prefix: `quarkus.<service-name>.` | the SDK client package name | `configName` | `apigatewayv2`, `eventbridge-scheduler` |
| `service-name-uppercase` | Display name, used in the title and throughout the text | the SDK descriptive service name: `serviceAbbreviation` of the AWS model, or `serviceFullName` | `displayName` | `ACM`, `Amazon S3`, `AWS STS` |
| `service-class-name` | Prefix of the SDK clients `<X>Client` / `<X>AsyncClient`, also used for the example resource classes | the SDK service name | — | `ApiGatewayV2`, `DynamoDb`, `CognitoIdentityProvider` |
| `extension-name` | Artifact `quarkus-amazon-<extension-name>`; names the configuration reference. Written only if it differs from `service-name`. | name of the service folder `services/<extension-name>/` | — | `scheduler` |
| `sdk-package` | SDK package `software.amazon.awssdk.services.<sdk-package>`. Written only if it differs from `extension-name`. | the SDK client package name | — | `cognitoidentityprovider` |
| `java-package` | Package of the example classes `org.acme.<java-package>`. Written only if it differs from `extension-name`. | the extension package name | `packageName` | `cognitouserpools` |
| `extension-status` | Status of the extension, also written to its extension descriptor. `deprecated` shows a WARNING under the title. Written only if it differs from `stable`. | `stable` | `status` | `deprecated` |

The file name is `amazon-<packageName>.adoc`, which can be overridden with `docsPageName`. It must match the page name `amazon-<page>.adoc`.

The display name is used as is, including the `Amazon` or `AWS` prefix of the AWS model: the title is `{service-name-uppercase} Client` (« ACM Client », « Amazon S3 Client »). Only override `displayName` when the model value is not readable (`AmazonApiGatewayV2`) or does not name the extension (`Amazon Cognito Identity Provider` for Cognito User Pools).

Real examples: [`_metadata/amazon-scheduler.adoc`](modules/ROOT/pages/_metadata/amazon-scheduler.adoc), [`_metadata/amazon-cognitouserpools.adoc`](modules/ROOT/pages/_metadata/amazon-cognitouserpools.adoc), and the overrides in [`services/cognito-user-pools/.../quarkus-customization.config`](../services/cognito-user-pools/src/main/resources/codegen-resources/quarkus-customization.config).

## `_description` attributes

The `_description/` file starts with the editorial attributes, if any, followed by the intro:

1. what the service is;
2. what this client does: control plane or data plane, API version, and which sibling extension to use for the rest (`To retrieve configuration data at runtime, use the AWS AppConfig Data extension.`).

Use the official service names (« AWS Lambda », « Amazon CloudWatch »).
Do not write the link to the AWS documentation: set `aws-docs-url`, and the page renders « For more information, see the {service-name-uppercase} documentation » after the intro.

| Attribute | Effect | Default | When to set it | Example |
|---|---|---|---|---|
| `aws-docs-url` | Link to the AWS documentation of the service, rendered after the intro | unset | always, with the user guide or the API reference of the service on docs.aws.amazon.com (not a product page) | `https://docs.aws.amazon.com/lambda/latest/dg/welcome.html` |
| `has-integration-test` | Says that no AWS account is required. Without it, the prerequisites warn that the local stacks may not emulate the service. | unset | only if the integration tests exercise the service against a local stack with real assertions | — |
| `aws-stack` | Local stack used by Dev Services, « Start … manually » and the local configuration examples: `floci` or `moto`. When it is not `floci`, the page shows the `quarkus.<service-name>.devservices.provider` property to set. | `floci` | only if the integration tests exercise the service with another stack (`quarkus.<service-name>.devservices.provider` in `integration-tests/src/main/resources/application.properties`) | `moto` |
| `solution-summary` | Shows the « Solution » section with a `quickstart`, « What you will build » without, and names the steps section « Walkthrough » instead of « Getting started »; the value is its first paragraph (inline formatting allowed) | unset | for a step-by-step guide | `The application built here allows to manage files stored in Amazon S3.` |
| `quickstart` | Adds the link to the completed example | unset | only if the folder exists in [quarkus-quickstarts](https://github.com/quarkusio/quarkus-quickstarts) | `amazon-s3-quickstart` |
| `main-class` | Class created by `mvn create`, also used by the generic usage | `Quarkus{service-class-name}SyncResource` | when your step-by-step code uses another class | `FruitResource` |
| `main-path` | `-Dpath` of `mvn create`, also used by the generic usage | `/sync` | together with `main-class` | `/fruits` |
| `needs-host-access` | « Start Floci manually » adds `--add-host=host.docker.internal:host-gateway` to `docker run`, so that the service can call the application from the container | unset | when the service calls back the application (SNS HTTP subscriptions) | — |
| `run-args` | System properties added to `java -jar` in « Packaging » | unset | when the example application needs them | `-Dkey.arn=$MASTER_KEY_ARN` |
| `extra-config-reference` | Adds the configuration reference of a related extension | unset | when a companion extension is documented on the same page | `dynamodb-enhanced` |

Real examples: [`_description/amazon-dynamodb.adoc`](modules/ROOT/pages/_description/amazon-dynamodb.adoc) (step-by-step guide with a quickstart), [`_description/amazon-iam.adoc`](modules/ROOT/pages/_description/amazon-iam.adoc) (step-by-step guide without a quickstart), [`_description/amazon-textract.adoc`](modules/ROOT/pages/_description/amazon-textract.adoc) (service not covered by the integration tests).

When a service has integration tests, give its guide a `usage`, `async-usage` and `run` example derived from them, and verify it against Dev Services.

## Injection points

An injection point is an optional file `pages/_extras/amazon-<page>-<point>.adoc`. If the file exists, it is included at that point. If it does not, nothing happens.

**A misnamed file is silently ignored.**

| Point | Where it is included | Mode | First line of the file | Real example |
|---|---|---|---|---|
| `usage` | after « Creating the Maven project » | **replaces** « Using the … client » | `:custom-usage:` | [`amazon-kms-usage.adoc`](modules/ROOT/pages/_extras/amazon-kms-usage.adoc) |
| `configuration` | end of « Configuring … clients » | appended | — | [`amazon-s3-configuration.adoc`](modules/ROOT/pages/_extras/amazon-s3-configuration.adoc) (`bucket.name`, create the bucket) |
| `run` | in « Run the app... », then again at the end of « Going asynchronous » with `run-async` set | appended | — | [`amazon-s3-run.adoc`](modules/ROOT/pages/_extras/amazon-s3-run.adoc) (browse frontend) |
| `async-usage` | in « Going asynchronous » | **replaces** the generic async resource | `:custom-async-usage:` | [`amazon-kms-async-usage.adoc`](modules/ROOT/pages/_extras/amazon-kms-async-usage.adoc) |
| `extras` | after the async clients, before « Configuration Reference » | appended | — | [`amazon-appconfigdata-extras.adoc`](modules/ROOT/pages/_extras/amazon-appconfigdata-extras.adoc), [`amazon-rds-extras.adoc`](modules/ROOT/pages/_extras/amazon-rds-extras.adoc) |

The `run` file is included twice: in « Run the application in Dev Mode » for the synchronous client, and at the end of « Going asynchronous » for the asynchronous one, with the `run-async` attribute set.
Wrap each part in the matching condition:

```asciidoc
ifndef::run-async[]
* Send messages to the queue with the synchronous client:
...
endif::[]
ifdef::run-async[]
* Call the same endpoints with the asynchronous client, replacing `sync` with `async` in the URLs.
endif::[]
```

A replacing file must start with its attribute (`:custom-usage:` or `:custom-async-usage:`), otherwise the generic content is rendered as well.

Files are included without `leveloffset`: write the headings at the level they have on the rendered page.

- `usage`: `===` sections, steps of « Walkthrough » (or « Getting started » without `solution-summary`).
- `configuration`: `====` subsections of « Configuring … clients » (create the resource, verify an address…), then `===` for a following step (S3: creating a frontend). The file must start with a `====` heading: it is included after « Use your AWS account », so text before the first heading would land in that subsection.
- `async-usage`, `run`: no heading; the text continues the section it is included in.
- `extras`: `==` top-level sections (S3 Transfer Manager, DynamoDB enhanced client, RDS IAM authentication, config sources). The file must start with a `==` heading: it is included after « Going further », so text before the first heading would land in that subsection. Put text about the async client in `async-usage`.

When the application needs a resource (a table, a queue, a key…), create it in the `configuration` file, in a single `==== Create the <resource>` subsection, starting with the application properties that name it.
Give the three ways to create it, each introduced by a block title:

```asciidoc
==== Create the SQS queue

.With Dev Services
Let Dev Services create the queue on startup:
...

.On a manually started Floci
Create the queue with the AWS CLI of the Floci container:
...

.On your AWS account
Create the queue with your own AWS CLI:
...
```

Real examples: [`amazon-sqs-configuration.adoc`](modules/ROOT/pages/_extras/amazon-sqs-configuration.adoc) (Dev Services property), [`amazon-dynamodb-configuration.adoc`](modules/ROOT/pages/_extras/amazon-dynamodb-configuration.adoc) (Dev Services init scripts).

## Writing rules

- Use the attributes rather than hard-coded values: `{service-name}`, `{service-name-uppercase}`, `{extension-name}`, `{java-package}`, `{main-class}`.
- Add `subs="attributes+"` to source blocks that contain attributes: `[source,java,subs="attributes+"]`.
- Do not repeat what the skeleton already renders: Dev Services, `docker run`, `aws configure`, HTTP client dependencies, local endpoint configuration, AWS credentials, configuration reference.
- In `_extras/`, CLI commands against a local Floci stack run inside the container: `docker exec floci aws <command>`. The CLI is preconfigured with the endpoint, the region and the credentials, so do not add `--profile` or `--endpoint-url`.
- With Moto, CLI commands use the profile created in « Start … manually » and its endpoint: `--profile moto --endpoint-url=http://localhost:5000`.
- Do not mention LocalStack in the service guides: it remains a supported provider, documented in the Dev Services guide only.
- When a command captures a value, add `--query <name> --output text` (the default JSON output cannot be parsed with `cut`), and `export` the variable if a later command or the application needs it.
- Never edit `_metadata/`. A value that the code generator cannot take from the service model goes to `_description/`.

## Checking the result

Render the pages with Asciidoctor from `docs/modules/ROOT/pages`, reporting missing attributes:

```shell
cd docs/modules/ROOT/pages
mkdir -p /tmp/docs-render
docker run --rm -u $(id -u):$(id -g) -v "$PWD":/documents:ro -v /tmp/docs-render:/out \
  asciidoctor/docker-asciidoctor:1.80 \
  asciidoctor -b html5 -a attribute-missing=warn -D /out amazon-<page>.adoc
```

Then check that:

- there is no warning;
- the `<h1>` is `{service-name-uppercase} Client`;
- the expected sections are there, each exactly once (see [What a page renders](#what-a-page-renders)).
