== Using AWS AppConfig Data as a Quarkus Config Source

In addition to injecting `AppConfigDataClient` / `AppConfigDataAsyncClient`, you can use the AWS AppConfig *Data* API as a configuration source.
When enabled, Quarkus starts a configuration session for your hosted configuration, loads the document, and exposes its entries as MicroProfile configuration properties.
The source then polls for updates on a fixed interval (unless you disable polling).

=== Enable the Config Source

Enable the config source by setting:

[source,properties]
----
quarkus.appconfigdata.config.enabled=true
----

=== Application, environment, and configuration profile

The config source calls `StartConfigurationSession` with the following identifiers (IDs or names, as accepted by AWS):

[source,properties]
----
quarkus.appconfigdata.config.enabled=true

quarkus.appconfigdata.config.application=my-application
quarkus.appconfigdata.config.environment=production
quarkus.appconfigdata.config.configuration-profile=my-profile
----

With these properties in place, you can read values like any other Quarkus configuration (for example via `@ConfigProperty` or `@ConfigMapping`), using the keys described below.

=== Optional polling settings

* `quarkus.appconfigdata.config.required-minimum-poll-interval-in-seconds` -- optional; sets the minimum interval between `GetLatestConfiguration` calls for the session, when required by your configuration profile.
* `quarkus.appconfigdata.config.update-interval` -- interval between polls after the initial load (default: `PT0S`). Set to or greater than `PT1S` to enable periodic polling.

=== How to get updated configuration properties

The following shows a resource implementation showing 2 ways for fetching a property which is updated through the App Config Data Config Source.

[source,java]
----
import static jakarta.ws.rs.core.MediaType.TEXT_PLAIN;

import jakarta.inject.Provider;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;

import org.eclipse.microprofile.config.ConfigProvider;
import org.eclipse.microprofile.config.inject.ConfigProperty;

@Path("/appconfigdata")
public class AppConfigDataResource {

    @ConfigProperty(name = "propertyName", defaultValue = "N/A")
    Provider<String> propertyName;  <1>

    @GET
    @Path("propertyName")
    @Produces(TEXT_PLAIN)
    public String getPropertyName() {
        return "property: " + propertyName.get(); <2>
    }

    @GET
    @Path("otherPropertyName")
    @Produces(TEXT_PLAIN)
    public String getOtherPropertyName() {
        return "property: " + ConfigProvider.getConfig().getValue("otherPropertyName", String.class); <3>
    }
}
----

<1> Declare variable name using `Provider<>`.
<2> Use the `Provider.get()` method to get the latest value of the property.
<3> Or use the `ConfigProvider` to get the latest observed value of the property.

=== How configuration keys are exposed

The hosted configuration body is parsed into a flat map of string keys and string values:

* If the document is **JSON**, nested objects are turned into dotted keys (for example `featureFlags.newCheckoutFlow` with value `true`).
* JSON **arrays** use index segments (for example `items[0].name`).
* If the document is **Java properties** format, standard `key=value` entries are exposed using those keys.

Boolean and numeric JSON values are exposed as strings (`true`, `false`, and the number's string form).

`quarkus.appconfigdata.config.format` accepts `auto` (default), `json`, `properties`, or `yaml` for this document source.
An explicit format overrides detection; unknown format names fail startup.
The shared `raw` format and non-null JSON scalars require a target property name, which this source does not provide, so they are rejected.
JSON `null`, `{}` and `[]` produce an empty configuration with `format=json`.

With `auto`, valid JSON objects and arrays take priority regardless of `Content-Type`.
Otherwise, a YAML `Content-Type` (including `application/yaml` and `text/yaml`) selects YAML, including flow-style YAML such as `{feature: true}`.
YAML decoding requires the optional `io.quarkus:quarkus-config-yaml` extension; explicit `format=yaml` fails startup without it.
This dependency is required for YAML decoding in all three AWS config sources (AppConfig Data, SSM and Secrets Manager).
With AppConfig Data `auto`, a YAML `Content-Type` still selects YAML when the extension is absent: decoding fails,
the previous snapshot is kept (or the source remains empty on the initial load), and there is no properties fallback.
Without a YAML `Content-Type`, `auto` does not detect nested YAML and reads it as properties instead.

[IMPORTANT]
====
Migration: YAML documents were previously read as Java properties. Nested YAML now exposes dotted keys, for example `feature.enabled`, instead of the old `feature` and `enabled` keys.

For this hosted document served with `Content-Type: application/yaml`:

[source,yaml]
----
feature:
  enabled: true
----

Before (Java properties interpretation):

[source,properties]
----
feature=
enabled=true
----

[source,java]
----
@ConfigProperty(name = "enabled")
boolean enabled; // true
----

The `feature` entry has an empty value, not a nested object; it cannot satisfy a required non-empty configuration value.

After (`format=auto` with the YAML extension installed, or explicit `format=yaml`):

[source,java]
----
@ConfigProperty(name = "feature.enabled")
boolean enabled; // true
----

The old `feature` and `enabled` keys are no longer exposed.
Set `quarkus.appconfigdata.config.format=properties` to retain the old interpretation.
====

=== Credentials, region, and endpoint

The config source uses the same AppConfig Data client configuration as the rest of the extension (credentials provider chain, region, and optional endpoint override).
This is useful for a local stack such as Floci, or for custom endpoints:

[source,properties]
----
quarkus.appconfigdata.endpoint-override=http://localhost:4566
quarkus.appconfigdata.aws.region=us-east-1
quarkus.appconfigdata.aws.credentials.type=static
quarkus.appconfigdata.aws.credentials.static-provider.access-key-id=test-key
quarkus.appconfigdata.aws.credentials.static-provider.secret-access-key=test-secret

quarkus.appconfigdata.config.enabled=true
quarkus.appconfigdata.config.application=my-application
quarkus.appconfigdata.config.environment=production
quarkus.appconfigdata.config.configuration-profile=my-profile
----

=== Load a configuration in the local stack

AppConfig Data only serves configurations that are deployed: a hosted configuration version alone is returned as an empty document, and the config source exposes no entries.
To try the config source with Dev Services, create the configuration and deploy it with an xref:dev-services.adoc#_init_scripts[init script], for example `src/test/resources/floci-init/01_setup_appconfigdata.sh`:

[source,bash]
----
#!/usr/bin/env bash
APPLICATION_ID=$(aws appconfig create-application --name my-application --query 'Id' --output text)
ENVIRONMENT_ID=$(aws appconfig create-environment --application-id "${APPLICATION_ID}" \
    --name production --query 'Id' --output text)
CONFIGURATION_PROFILE_ID=$(aws appconfig create-configuration-profile --application-id "${APPLICATION_ID}" \
    --name my-profile --location-uri hosted --type AWS.Freeform --query 'Id' --output text)

VERSION_NUMBER=$(aws appconfig create-hosted-configuration-version --application-id "${APPLICATION_ID}" \
    --configuration-profile-id "${CONFIGURATION_PROFILE_ID}" \
    --content "$(echo '{"greeting": "hello"}' | base64)" --content-type application/json \
    --query 'VersionNumber' --output text /dev/null)

DEPLOYMENT_STRATEGY_ID=$(aws appconfig create-deployment-strategy --name all-at-once \
    --deployment-duration-in-minutes 0 --growth-factor 100 --final-bake-time-in-minutes 0 \
    --replicate-to NONE --query 'Id' --output text)

aws appconfig start-deployment --application-id "${APPLICATION_ID}" --environment-id "${ENVIRONMENT_ID}" \
    --configuration-profile-id "${CONFIGURATION_PROFILE_ID}" --configuration-version "${VERSION_NUMBER}" \
    --deployment-strategy-id "${DEPLOYMENT_STRATEGY_ID}"

echo "#### Init completed"
----

The script uses the AWS CLI, so select the Floci image that ships it.
The config source loads the configuration when the application starts, so also make Dev Services wait for the script to complete:

[source,properties]
----
quarkus.aws.devservices.floci.image-name=floci/floci:latest-compat
quarkus.aws.devservices.floci.init-scripts-folder=src/test/resources/floci-init
quarkus.aws.devservices.floci.init-completion-msg=#### Init completed

quarkus.appconfigdata.config.enabled=true
quarkus.appconfigdata.config.application=my-application
quarkus.appconfigdata.config.environment=production
quarkus.appconfigdata.config.configuration-profile=my-profile
----

The `greeting` property then resolves to `hello`.

=== Notes and limitations

* The config source keeps an internal snapshot that is updated when polling succeeds; components that only read configuration at startup will not see later changes unless they observe configuration dynamically.
* Invalid JSON or Java properties content is logged as an error and leaves the previous snapshot unchanged. Polling continues using the next token returned by AppConfig Data.
* Invalid UTF-8 and invalid or recursive YAML also leave the previous snapshot unchanged. Logs classify failures without including SDK/parser messages, values or polling tokens. SDK retries run before a failed call is reported; no extra retry loop is added.
* A zero-byte response means the configuration is unchanged. A valid empty document (such as `{}` or `[]`), or a whitespace-only properties document, replaces the snapshot with an empty configuration.
* If identifiers are missing or AppConfig Data returns an error during session start or fetch, Quarkus logs the error and the config source may expose no entries from AppConfig for that attempt.
