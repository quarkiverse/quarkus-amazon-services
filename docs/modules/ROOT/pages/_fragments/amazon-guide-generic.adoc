NOTE: The {service-name-uppercase} extension is based on https://docs.aws.amazon.com/sdk-for-java/v2/developer-guide/welcome.html[AWS Java SDK 2.x].
It's a major rewrite of the 1.x code base that offers two programming models (Blocking & Async).

The Quarkus extension supports two programming models:

* Blocking access using URL Connection HTTP client (by default), the Apache HTTP Client or the AWS CRT-based HTTP client
* https://docs.aws.amazon.com/sdk-for-java/v2/developer-guide/basics-async.html[Asynchronous programming] based on JDK's `CompletableFuture` objects and the Netty HTTP client or the AWS CRT-based HTTP client

In this guide, we see how you can get your REST services to use {service-name-uppercase} locally and on AWS.

== Prerequisites

To complete this guide, you need:

* JDK {jdk-version} installed with `JAVA_HOME` configured appropriately
* an IDE
* Apache Maven {maven-version}
* Docker, to run {service-name-uppercase} locally with Dev Services and to run the tests
* Optionally, GraalVM or Mandrel installed to build a native executable

ifdef::has-integration-test[]
No AWS account is required: Dev Services and the local {aws-stack-name} container provide everything you need.
You only need an AWS account and the https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-install.html[AWS Command Line Interface] if you want to deploy to AWS.
endif::[]
ifndef::has-integration-test[]
[NOTE]
====
The integration tests of the {service-name-uppercase} extension do not run against a local stack, so this guide cannot guarantee that {aws-stack-name}, or any other xref:dev-services.adoc[supported stack], emulates {service-name-uppercase}, or all of its operations.
Check the documentation of the stack you use.
If it does not emulate the operations you need, disable Dev Services with `quarkus.{service-name}.devservices.enabled=false` and use an AWS account with the https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-install.html[AWS Command Line Interface].
====
endif::[]

=== Provision {service-name-uppercase} locally via Dev Services

The easiest way to start working with {service-name-uppercase} is to run a local instance using Dev Services.
ifeval::["{aws-stack}" != "floci"]
Dev Services uses Floci by default. This guide uses {aws-stack-name}, so select it in `application.properties`:

[source,properties,subs="attributes+"]
----
quarkus.{service-name}.devservices.provider={aws-stack}
----

endif::[]
Dev Services starts a {aws-stack-name} container in dev and test modes, and configures the client to use it, so you don't need an AWS account.

The container listens on a random port, so you never hard-code an endpoint.
It is labelled `quarkus-dev-service-{aws-stack}` and shared between the Quarkus applications running in dev mode.
Refer to xref:dev-services.adoc[Dev Services for Amazon Services] for the provider selection, the container configuration and the init scripts.

=== Provision {service-name-uppercase} locally manually

You can also set up a local version of {service-name-uppercase} manually, first start a {aws-stack-name} container:

ifeval::["{aws-stack}" == "floci"]
[source,bash,subs="verbatim,attributes"]
----
docker run --rm --name floci --publish 4566:4566 -d floci/floci:latest-compat
----
This starts a Floci instance that is accessible on port `4566`. Floci exposes all the services it emulates on this single endpoint.

The `latest-compat` image ships the AWS CLI, already configured to target the local endpoint.
Run the provisioning commands of this guide inside the container, with `docker exec floci aws ...`.
You do not need to install or configure the AWS CLI on your host.

You can check the region, the credentials and the endpoint used inside the container:

[source,bash,subs="verbatim,attributes"]
----
docker exec floci env | grep AWS_
----

The CLI uses the region `us-east-1`, the credentials `test` / `test`, and the endpoint `http://localhost:4566` seen from inside the container.
An application running on the host reaches Floci at `http://localhost:4566`; an application running in another container must use the container name, for example `http://floci:4566`, and the containers must share a Docker network.
endif::[]
ifeval::["{aws-stack}" == "moto"]
[source,bash,subs="verbatim,attributes"]
----
docker run --rm --name moto --publish 5000:5000 -d motoserver/moto:latest
----
This starts a Moto instance that is accessible on port `5000`.

Create an AWS profile for your local instance using AWS CLI:
[source,shell,subs="verbatim,attributes"]
----
$ aws configure --profile {aws-stack}
AWS Access Key ID [None]: test-key
AWS Secret Access Key [None]: test-secret
Default region name [None]: us-east-1
Default output format [None]:
----
endif::[]

== Creating the Maven project

First, we need a new project. Create a new project with the following command:

[source,bash,subs=attributes+]
----
mvn io.quarkus.platform:quarkus-maven-plugin:{quarkus-version}:create \
    -DprojectGroupId=org.acme \
    -DprojectArtifactId=amazon-{extension-name}-quickstart \
    -DclassName="org.acme.{java-package}.{main-class}" \
    -Dpath="{main-path}" \
    -Dextensions="rest-jackson,amazon-{extension-name}"
cd amazon-{extension-name}-quickstart
----

This command generates a Maven structure importing the Quarkus REST and {service-name-uppercase} Client extensions.
After this, the `amazon-{extension-name}` extension has been added to your `pom.xml`, along with `quarkus-rest` and `quarkus-rest-jackson`.

The {service-name-uppercase} extensions are a component of the Quarkus platform, and the generated `pom.xml` already imports their BOM through it, which is the recommended setup.

Due to differing release schedules, the Quarkus platform may not include the latest Quarkus Amazon Services release.
If you need features from a newer release, replace the generated `quarkus-amazon-services-bom` import with the Quarkus Amazon Services BOM:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.quarkiverse.amazonservices</groupId>
    <artifactId>quarkus-amazon-services-bom</artifactId>
    <version>{quarkus-amazon-services-version}</version>
    <type>pom</type>
    <scope>import</scope>
</dependency>
----

The command also generates a `{main-class}Test` class and a `{main-class}IT` class that call the `hello` endpoint of the generated resource.
The next section replaces that resource: delete these two files, or update them to match the endpoints you create.

== Using the {service-name-uppercase} client

The extension exposes the synchronous and asynchronous {service-name-uppercase} clients of the AWS SDK as CDI beans, so you only need to inject them.

Edit the `org.acme.{java-package}.{main-class}` REST resource created by the previous command to inject the synchronous client:

[source,java,subs="attributes+"]
----
package org.acme.{java-package};

import jakarta.inject.Inject;
import jakarta.ws.rs.Path;

import software.amazon.awssdk.services.{sdk-package}.{service-class-name}Client;

@Path("{main-path}")
public class {main-class} {

    @Inject
    {service-class-name}Client client;

    // Call the client from your endpoints
}
----

To inject several clients with different configurations, refer to the xref:common-features.adoc[named clients] support.
endif::[]

== Configuring {service-name-uppercase} clients

Both {service-name-uppercase} clients (sync and async) are configurable via the `application.properties` file that can be provided in the `src/main/resources` directory.
Additionally, you need to add to the classpath a proper implementation of the sync client. By default, the extension uses the URL connection HTTP client, so
you need to add a URL connection client dependency to the `pom.xml` file:

[source,xml]
----
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>url-connection-client</artifactId>
</dependency>
----

If you want to use the Apache HTTP client instead, configure it as follows:
[source,properties,subs=attributes]
----
quarkus.{service-name}.sync-client.type=apache
----

And add the following dependency to the application `pom.xml`:
[source,xml]
----
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>apache-client</artifactId>
</dependency>
----

If you want to use the AWS CRT-based HTTP client instead, configure it as follows:
[source,properties,subs=attributes]
----
quarkus.{service-name}.sync-client.type=aws-crt
----

And add the following dependency to the application `pom.xml`:
[source,xml]
----
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>aws-crt-client</artifactId>
</dependency>
----

If you provisioned a local {service-name-uppercase} instance manually (for example {aws-stack-name}), configure the client to use it as follows:

[source,properties,subs="attributes+"]
----
quarkus.{service-name}.endpoint-override=http://localhost:{aws-stack-port} <1>

quarkus.{service-name}.aws.region=us-east-1 <2>
quarkus.{service-name}.aws.credentials.type=static <3>
quarkus.{service-name}.aws.credentials.static-provider.access-key-id=test-key
quarkus.{service-name}.aws.credentials.static-provider.secret-access-key=test-secret
----
<1> Override the {service-name-uppercase} client to use {aws-stack-name} instead of the actual AWS service. When it is set, Dev Services does not start a local stack for {service-name-uppercase}.
<2> {aws-stack-name} defaults to `us-east-1`
<3> The `static` credentials provider lets you set the `access-key-id` and `secret-access-key` directly

If you want to work with an AWS account, you need an AWS account with access to {service-name-uppercase} and the https://docs.aws.amazon.com/cli/latest/userguide/cli-chap-install.html[AWS Command Line Interface], then remove or comment out the `endpoint-override` and the static credentials properties above.
By default, the {service-name-uppercase} client extension uses the `default` credentials provider chain that looks for credentials in this order:

* Java System Properties - `aws.accessKeyId` and `aws.secretAccessKey`
* Environment Variables - `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`
* Credential profiles file at the default location (`~/.aws/credentials`) shared by all AWS SDKs and the AWS CLI
* Credentials delivered through the Amazon ECS if the `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` environment variable is set and the security manager has permission to access the variable,
* Instance profile credentials delivered through the Amazon EC2 metadata service

And the region from your AWS CLI profile will be used.

[IMPORTANT]
====
Without `endpoint-override`, Dev Services starts a local stack for {service-name-uppercase} in dev and test modes, and the client uses it instead of your AWS account.
Removing the `endpoint-override` is therefore not enough to use your AWS account in these modes: also disable Dev Services for {service-name-uppercase}:

[source,properties,subs="attributes+"]
----
quarkus.{service-name}.devservices.enabled=false
----

Dev Services never starts in production mode.
====

== Run the application in Dev Mode

Run the application in dev mode with:

[source,bash,subs="verbatim,attributes"]
----
./mvnw clean quarkus:dev
----

Unless you set `endpoint-override`, Dev Services starts a {aws-stack-name} container and configures the {service-name-uppercase} clients to use it.
The Dev Services card of the Dev UI, at http://localhost:8080/q/dev-ui, shows the container and the endpoint it exposes.

ifndef::custom-usage[]
The REST resource does not expose any endpoint yet: add methods that call the client, then call them with `curl http://localhost:8080{main-path}/...`.
endif::[]

=== Packaging

Packaging your application is as simple as `./mvnw clean package`.
ifdef::run-args[]
It can then be run with `java {run-args} -jar target/quarkus-app/quarkus-run.jar`.
endif::[]
ifndef::run-args[]
It can then be run with `java -jar target/quarkus-app/quarkus-run.jar`.
endif::[]

With GraalVM or Mandrel installed, you can also create a native executable binary:

[source,bash,subs="verbatim,attributes"]
----
./mvnw clean package -Dnative
----

Without GraalVM or Mandrel, build the native executable inside a container:

[source,bash,subs="verbatim,attributes"]
----
./mvnw clean package -Dnative -Dquarkus.native.container-build=true
----

Depending on your system, that will take some time.
ifdef::run-args[]
Run the native executable with `./target/amazon-{extension-name}-quickstart-1.0.0-SNAPSHOT-runner {run-args}`.
endif::[]
ifndef::run-args[]
Run the native executable with `./target/amazon-{extension-name}-quickstart-1.0.0-SNAPSHOT-runner`.
endif::[]

NOTE: Dev Services does not start in production mode, so you need to make sure that your `application.properties` file is configured to use your AWS account or a local stack.
To use a local {aws-stack-name} instance, pass the endpoint and the credentials on the command line:

[source,bash,subs="verbatim,attributes"]
----
java \
    -Dquarkus.{service-name}.endpoint-override=http://localhost:{aws-stack-port} \
    -Dquarkus.{service-name}.aws.region=us-east-1 \
    -Dquarkus.{service-name}.aws.credentials.type=static \
    -Dquarkus.{service-name}.aws.credentials.static-provider.access-key-id=test-key \
    -Dquarkus.{service-name}.aws.credentials.static-provider.secret-access-key=test-secret \
    -jar target/quarkus-app/quarkus-run.jar
----

See the {quarkus-guides-url}/packaging[Packaging applications] guide for more details.

=== Going asynchronous

Thanks to the AWS SDK v2.x used by the Quarkus extension, you can use the asynchronous programming model out of the box.

include::../_extras/{docname}-async-usage.adoc[opts=optional]

ifndef::custom-async-usage[]
Create a `org.acme.{java-package}.Quarkus{service-class-name}AsyncResource` REST resource that will be similar to our `{main-class}` but using the asynchronous client:

[source,java,subs="attributes+"]
----
package org.acme.{java-package};

import jakarta.inject.Inject;
import jakarta.ws.rs.Path;

import software.amazon.awssdk.services.{sdk-package}.{service-class-name}AsyncClient;

@Path("/async")
public class Quarkus{service-class-name}AsyncResource {

    @Inject
    {service-class-name}AsyncClient client;

    // Call the client from your endpoints
}
----

The methods of the asynchronous client return `CompletableFuture` objects, which you can turn into Mutiny `Uni` instances with `Uni.createFrom().completionStage(...)`.
endif::[]

To enable the asynchronous client, you also need to add the Netty HTTP client dependency to the `pom.xml`:

[source,xml]
----
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>netty-nio-client</artifactId>
</dependency>
----

If you want to use the AWS CRT-based HTTP client instead, configure it as follows:
[source,properties,subs=attributes]
----
quarkus.{service-name}.async-client.type=aws-crt
----

And add the following dependency to the application `pom.xml`:
[source,xml]
----
<dependency>
    <groupId>software.amazon.awssdk</groupId>
    <artifactId>aws-crt-client</artifactId>
</dependency>
----
